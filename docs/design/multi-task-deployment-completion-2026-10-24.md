# 多任务平台补齐：源生命周期、持久化部署与多模型角色

日期：2026-10-24。本轮是实现记录，不是生产能力验收。

## 不变边界

- 新任务仍只允许 shadow，production 保持 NO-GO。
- legacy 的 ModelReleaseService、SceneGuard、baseline、校准和可信 soak 不减少。
- 不改源视频；本机仅普通功能与模拟测试，不运行真实训练、识别或媒体采集。
- 保留现有工作区修改，不自动提交或推送。

## 本轮交付顺序

1. 摄像头源可独立于 legacy 模型初始化启停，采集所有权唯一。
2. managed 任务部署使用数据库期望状态、操作收据、版本并发控制和显式对账；重启与回滚必须核验完整绑定。
3. 内置多角色模板及逐角色前端选择，不能只取第一个模型角色。

## 已补齐的控制流程

### 独立源与 legacy 生命周期

- `CameraManager.start_source()` 只建立唯一采集源；不初始化 legacy 检测头。legacy 初始化失败时，源、预览和其它任务仍可保留。
- legacy 使用只读共享源的独立订阅，其必要的原地图像变换只作用于自己的像素副本。停止单个任务不能关闭源。
- 显式停止整个源会先撤销源代次并取消所有所属任务，再确认采集资源清理；清理未确认时保留所有权和可重试状态，不假报停止。
- 新增鉴权的 `/api/cameras/{camera_id}/source` 读接口及 `/source/start`、`/source/stop` 命令。旧整相机操作保留兼容语义，不隐式替代源操作。

### 任务持久化部署

- `TaskDeploymentService` 是 managed 任务部署意图的数据库写入入口；`TaskDeploymentCoordinator` 负责有界后台执行、观察及重启对账。legacy 仍使用原 `ModelReleaseService`，二者不能互相发布。
- `/api/analysis-tasks/{task_id}/deployments` 接收幂等键和期望部署修订号，返回 `202 + operation_id`。期望执行包、已应用执行包、当前操作及运行观察分别保存。
- 在同一写事务中复查任务、相机、模板、配置版本和摘要。期望运行期间拒绝改配置或归档，必须先登记并确认停止。
- 候选执行包全部准备及身份核验后再切换。加载或资源准入失败保留旧运行实例；切换失败需要补偿及对账，不能将未知结果当成成功。
- 停止和重新部署都有单调的修订号水位，旧部署、旧停止和旧帧不能越过当前身份。重复使用同一执行包也必须切换运行时代次并清空旧结果。
- 启动时只从数据库授权的 applied 包及操作记录恢复，不扫描模型目录。源缺席、场景未就绪分别显示 `waiting_source`、`waiting_scene`，不自动开源或批准场景。
- 结果未知时保留原幂等键及请求内容；未知提交错误返回 5xx，不错误归类为可直接换键的 409。协调器通过每数据库的操作系统互斥所有权防止双重管理，未确认清理不能释放所有权。
- 原非持久化 `/runtime/start`、`/runtime/stop` 写入口返回明确冲突，引导到持久化部署，避免停止后重启又恢复的双写歧义。

### 回滚与历史配置恢复

同配置回滚必须指向同任务曾实际 applied 的包。跨配置不能直接将旧包冒充当前配置运行：人工在确认的持久化停止后，通过 `configuration-restores` 重新核验旧模型制品，原子生成新 `TaskRevision`、新执行包及不可变恢复收据，再显式部署。

恢复收据查询优先于运行时停止检查，因此首次提交成功但响应丢失后，仍可用同一请求重试，不会因后来已开机而丢失已提交身份。恢复不改变旧配置、审批和包摘要，不自动部署或增加生产权限。

执行包列表提供 `historically_applied`，从同任务全部 applied 非 stop 收据计算，不依赖界面只展示的最近 100 条记录。

### 多模型角色与界面

- 新增固定旁路模板 `ppe_compliance_dual.v1`，明确 `person_detector`、`head_detector` 两个角色；原单模型 PPE 模板保留。
- 兼容性按角色检查适配器、标签、任务标签及 camera scope。前端解释不兼容原因，后端仍是最终权威。
- 冻结和执行时必须完整匹配所有角色，全部模型校验并加载后才能 ready；同帧任一角色失败不输出部分成功。
- 相机详情分别显示源控制和任务持久化部署；明确区分已登记、等待条件和已应用。历史配置恢复不自动选择或部署新包。
- 前端为读取、命令及任务切换分别设置代次，保护同任务多次刷新、跨任务切换和迟到请求；不将其它任务的回执或错误套到当前任务。
- Windows CUDA worker 显式调用 ORT 官方 `preload_dlls()` 发现已安装的 Torch/NVIDIA DLL，不依赖父进程加载或修改 PATH。预加载失败明确受阻，构造与图节点的 CPU 回退禁令不变；CPU 任务不触发 CUDA 加载。

## 仍未完成的目标

这些补丁不等于 P3—P6 生产闭环全部完成。新任务仍是旁路：专属生产验收/签名协议、内置检测/姿态训练执行器、外部标注工具的真实上传回传闭环、非周期自动采集、真实多模型吞吐和业务质量验收仍需后续交付。双模型 PPE 尚未接入单制品的外部训练导入配方，不能宣称其端到端训练已完成。

真实 GPU 冒烟只能证明受控工作进程、CUDA 执行和生命周期可运行，不能证明异物召回率、安全帽判断质量、快速运动延迟或 72 小时稳定性。原 SceneGuard、baseline v3、校准、独立人工审批和可信 soak 要求均保持不变。

## 验证方式

本机使用 `run_local_functional_tests.py` 的模型 SDK/训练/相机与视频读取拦截，前端使用普通单测及临时数据库隔离浏览器服务。硬件测试在用户授权的局域网测试机执行，必要源码以带逐文件 SHA256 的独立快照复制；不传运行数据、视频、备份或连接凭据。实际结果在本节完成后记录，尚未结束的验证不得计为通过。
